# PRD Alignment Implementation Plan

> **For Hermes:** Use the Codex worker to implement each phase task-by-task. Do not deploy Production without explicit approval.

**Goal:** เติมส่วนที่ยังขาดจาก PRD ให้ MVP ครบเส้นทาง LINE Chat → AI → LIFF Verify → Supabase → Dashboard/ประวัติ/LINE summary โดยรักษาความปลอดภัยและความเรียบง่ายของระบบเดิม

**Architecture:** คง Express + Vercel + Supabase + Gemini + LINE LIFF เป็นแกนหลัก เพิ่ม LINE Messaging Webhook เป็นทางเข้าอีกทางหนึ่ง และเพิ่ม API/UI สำหรับประวัติรายการที่กรองด้วย LINE user identity ทุก request. ใช้ idempotency จาก LINE event/message ID และเก็บ pending slip แบบ durable เพื่อให้ webhook retry ไม่สร้างรายการซ้ำ

**Tech Stack:** Node.js/TypeScript, Express, Multer, LINE Messaging API/Content API, LIFF SDK, Gemini, Supabase PostgreSQL/Storage, Vitest, Vercel

---

## สถานะปัจจุบัน

ทำเสร็จแล้ว:

- LIFF authentication จริงและ Bearer token verification
- LIFF upload → Gemini extraction → verify/edit → save
- Supabase durable persistence และ private user scoping
- Dashboard รายเดือนพร้อม KPI/charts
- UI status, retry, hidden-state fix และ refresh หลัง save

ยังขาดตาม PRD:

- **FR-01/Flow A:** LINE Messaging Webhook รับรูปจากแชท, ดาวน์โหลด LINE Content API, สร้าง pending slip และตอบกลับอย่าง idempotent
- **FR-05:** Transaction History, search/filter, รายละเอียด และภาพสลิปต้นฉบับ
- **FR-06:** Flex Message สรุปหลังบันทึกสำเร็จ
- Dashboard ส่วนที่ PRD ระบุเพิ่มเติม: เลือกช่วงเวลาและรายการล่าสุด
- **FR-07, export, multi-currency:** เป็นงานต่อยอด ไม่อยู่ใน critical path ของ MVP รอบนี้

## ลำดับดำเนินงาน

### Phase 3.1 — LINE Chat Webhook และ pending-slip pipeline

**Dependency:** LINE channel credentials, webhook URL, Content API scope, ตาราง pending slips และ idempotency key

1. เขียน failing tests สำหรับ signature verification, event filtering และ duplicate event id
2. เพิ่ม webhook route ที่ตรวจ `x-line-signature` ด้วย channel secret โดยไม่ log body/secret
3. รองรับเฉพาะ image message; event อื่นตอบ 200 โดยไม่ทำงานซ้ำ
4. ดาวน์โหลดภาพจาก LINE Content API ด้วย access token ฝั่ง server
5. ตรวจ MIME/ขนาดด้วย validator เดิม แล้วเก็บภาพใน Supabase Storage
6. เรียก Gemini extraction และสร้าง pending slip ที่ผูกกับ `line_user_id` และ LINE event/message ID
7. ส่ง reply/Flex ที่มีข้อมูลที่อ่านได้และปุ่มเปิด LIFF พร้อม upload reference
8. เพิ่ม unique constraint/idempotency handling และ retry-safe behavior
9. ทดสอบ integration ด้วย mocked LINE/Gemini/Supabase clients และ run full suite

**Acceptance:** ส่งรูปใน LINE แล้วได้ข้อความตอบกลับพร้อมปุ่มเปิด LIFF; retry webhook เดิมไม่สร้างภาพ/รายการซ้ำ; invalid signature ถูกปฏิเสธ

### Phase 3.2 — LIFF verification จาก webhook และ Flex summary หลัง save

**Dependency:** Phase 3.1 และ signed pending-slip contract เดิม

1. เขียน failing tests ให้ pending upload จาก webhook เปิดใน LIFF ได้โดยยังตรวจ ownership
2. เพิ่ม deep-link/query state สำหรับเลือก pending upload โดยไม่ bypass Bearer auth
3. แสดงข้อมูล extraction ในฟอร์มเดิมและให้แก้ไขได้
4. หลัง save สำเร็จ เรียก LINE Messaging API ส่ง Flex summary ไปยังเจ้าของรายการ
5. ทำให้การส่ง summary ล้มเหลวไม่ rollback transaction และไม่เปิดเผย provider error ให้ผู้ใช้
6. เพิ่ม idempotency สำหรับการส่ง summary และ tests ของ failure path

**Acceptance:** ผู้ใช้แก้ไขและบันทึกรายการจากภาพในแชทได้; transaction ถูกบันทึกครั้งเดียว; ได้ summary ใน LINE เมื่อส่งได้; save ยังสำเร็จแม้ LINE reply ล้มเหลว

### Phase 3.3 — Transaction History และรายละเอียดรายการ

**Dependency:** transactions/slips schema และ Phase 3.2

1. เขียน failing tests สำหรับ list user-scoping, sort, pagination, search และ filters
2. เพิ่ม `GET /api/transactions` พร้อม date/type/category/search/page parameters และ validation
3. เพิ่ม `GET /api/transactions/:id` ที่บังคับ `line_user_id` ownership
4. เพิ่ม signed short-lived image URL หรือ server proxy สำหรับภาพใน private bucket; ห้ามส่ง service-role URL ตรงไป frontend
5. เพิ่ม mobile-first history list ใน LIFF พร้อม empty/loading/error states
6. เพิ่ม detail view/modal แสดงข้อมูลและภาพต้นฉบับ
7. ทดสอบผู้ใช้ A อ่านข้อมูลผู้ใช้ B ไม่ได้ (404/403 ตาม contract) และทดสอบ pagination

**Acceptance:** ผู้ใช้เห็นเฉพาะรายการของตนเอง ค้นหา/กรอง/เรียงได้ และเปิดดูรายละเอียดพร้อมภาพสลิปได้

### Phase 3.4 — Dashboard ให้ตรง PRD

**Dependency:** Phase 3.3 API contract

1. เขียน failing tests สำหรับ today/current month/custom range และ timezone Bangkok
2. เพิ่ม query parameters และ validated bounds ใน dashboard API
3. เพิ่มตัวเลือกช่วงเวลาใน UI โดย default เป็นเดือนนี้
4. เพิ่ม recent list 5 รายการล่าสุดพร้อม category/type icon และลิงก์ไป detail
5. คง empty state ที่ไม่แสดง warning/skeleton เมื่อไม่มีปัญหา
6. หลัง save ให้ refresh dashboard/recent list และรักษา auth error behavior

**Acceptance:** Dashboard เลือกช่วงเวลาได้, KPI/charts/recent list ใช้ช่วงเดียวกัน, timezone ไม่เลื่อนวัน และ empty state สื่อความหมายชัดเจน

### Phase 3.5 — Production hardening และ E2E gate

1. ตรวจ Supabase migrations, RLS/policies, unique indexes และ Storage private policy
2. ตรวจ LINE webhook endpoint, channel secret handling, scopes และ LIFF endpoint
3. เพิ่ม safe structured error logging ที่ไม่มีภาพ/token/key/PII เกินจำเป็น
4. รัน `npm test`, `npm run build`, `git diff --check` และ secret scan
5. ทดสอบ E2E ด้วยสลิปจริงผ่าน LINE: upload, extraction, edit, save, Flex, history, image, dashboard
6. ตรวจ duplicate webhook/retry และ cross-user isolation
7. Deploy แยกเป็น phase หลังผู้ใช้อนุมัติเท่านั้น และตรวจ live endpoints/logs หลัง deploy
